## `repo-plans` の作業規約

このディレクトリは、新しいリポジトリを作る際の計画と探索を管理する。既存コードの変更計画と異なり、実装、構造、ドキュメント、エージェント規約を同時に確定させない。フェーズは `01-specification-and-technology/`、`02-minimal-delivery/`、`03-foundation/` の順に進め、前フェーズが完了するまで後続フェーズの計画を作らない。

計画を新規作成・更新・実行する前に、現在の場面に対応するファイルを読む。

| 場面                                                     | 読む場所                                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 作業を始める・再開する                                   | [asis.md](asis.md)、[phase-status.md](phase-status.md)                                                        |
| 計画ファイルを作る（ファイル名、frontmatter、`status`）  | [plan-format.md](guides/plan-format.md)、[plan-skeleton.md](guides/plan-skeleton.md)    |
| ラフ案（仮説・着想）を書く                               | [plan-format.md の「ラフ案の status」](guides/plan-format.md#ラフ案の-status)                      |
| 仕様・技術を確定する                                     | [01-specification-and-technology.md](guides/01-specification-and-technology.md)                    |
| 最小の縦切りを実装・検証する                             | [02-minimal-delivery.md](guides/02-minimal-delivery.md)                                            |
| ドキュメント、ルール、スキルの基盤を定着する             | [03-foundation.md](guides/03-foundation.md)                                                        |
| ユーザーへの質問、レビュー依頼、フィードバック反映を行う | [interaction-loop.md](guides/interaction-loop.md)                                                  |
| 計画を `complete` にする                                 | [phase-gate.md](guides/phase-gate.md)                                                              |
| 3フェーズを通した記入例を見る                            | [references/](references/README.md)                                                         |

### リポジトリのルートと配置

「リポジトリのルート」は、`repo-plans/` をコピーした先の親ディレクトリ（`repo-plans/` を含む階層）を指す。`repo-plans/` 配下ではない。README、エージェント指示ファイル、設定ファイルはルートに置く。ルール・スキルを置くときは、置き場所をルートからの相対パスで計画に書く。

`guides/` と `references/` は読むだけで書き換えない。運用中に書き換えるのは、`repo-plans/` 直下の `asis.md`・`phase-status.md` と、フェーズフォルダ・`rough/`・`progress/` の中の計画だけである。

実験・評価・観察の記録は、対象リポジトリの外に置く。対象リポジトリの検査（リンク検査など）に混入するためである。

### 作業前

1. [asis.md](asis.md) を読み、現在のフェーズと次の作業を確認する。
2. ルートの案内文、既存のエージェント指示、すでにある設定ファイルを読む。
3. 現在のフェーズのフォルダに、[plan-format.md](guides/plan-format.md) の命名で計画を書く（新規なら [plan-skeleton.md](guides/plan-skeleton.md) をコピーする）。
4. ユーザーの回答が必要な質問と、作業後にレビューできる事項を分けて記載する。
5. 既存のルールまたはスキルがあれば先に読む。存在しないなら、今回の作業で必要な最小限だけを新設する。

### 実装中

- 最初に、利用者または呼び出し元から観測できる最小の縦切りを完成させる。将来必要になる抽象化、ディレクトリ、設定を先回りして追加しない。
- 一度の計画は、同じ目的と完了条件を持つ検証可能な範囲に限定する。範囲が広がったら、新しい計画として切り出す。
- 仮説、検討中の案、実装の正本を混在させない。仮説は `rough/`、実行手順は計画、恒久的な規約はルールまたはスキルに置く。
- ルールは短く、観測可能な行動として書く。「なぜ」を補う必要がある場合だけ、近くの文書へのリンクを付ける。
- スキルは反復する判断・手順にだけ作る。単発の実装経緯をスキルへ移さない。
- 新たなツール、依存関係、外部サービス、生成物、破壊的な変更を導入する前に、目的、代替案、検証方法、保守担当を計画へ記録する。
- 初期案を作ったら、ユーザーに提示する。決定が必要なら具体的な選択肢を添えて質問し、実装結果なら検証可能なレビュー項目を示す。
- ユーザーのフィードバックを受けたら、採否と変更内容を計画へ反映してから次の作業へ進む。フィードバック待ちの仮説を確定事項として扱わない。

### ルール化とスキル化の基準

- ルールにする: 次の作業でも守る行動で、観測可能に書けるもの。計画に残る実績が1回でも、違反の影響が大きければよい。ただし実績が1回だけの項目には、その旨と見直し条件を添える。
- スキルにする: 同じ判断・手順を2回以上繰り返し、手順が3ステップ以上になるもの。実績が1回なら作らず、反復した時点で作る。
- どちらにも当たらない知見は、計画かドキュメントに残す。

### 作業後

1. 計画に書いた完了条件を検証し、結果を記録する。`complete` にするには [フェーズ完了ゲート](guides/phase-gate.md) を満たす。
2. ユーザーからの質問・レビュー・フィードバックを少なくとも一度経たことを確認する。
3. 以後も守るべき知見はルールまたはスキルへ移す。移した場合は計画に参照先を残す。
4. 次の作業に必要な未決事項だけを、次の計画または引継ぎとして残す。実装済みの事実と計画が異なる場合は計画を更新する。
5. [asis.md](asis.md) と [phase-status.md](phase-status.md) を更新する。
6. リポジトリのルートで検査を実行し、エラーが無くなるまで直す（標準ライブラリのみ。`uv` が無ければ `python` でよい）。

   ```bash
   uv run repo-plans/lint_repo_plans.py repo-plans
   ```

### ポータビリティ

- 特定のAIエージェント、IDE、OS、シェル、言語、ホスティング、パッケージマネージャを前提に書かない。
- ツール固有の設定が必要なら、そのツールを使う理由と代替時に維持すべき行動を併記する。
- このファイルはサブフォルダにあり、ルートで作業するエージェントは自動では読まない。導入時にルートの指示ファイルから参照し、フェーズ3の完了時にその参照を外す。

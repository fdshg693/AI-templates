# フェーズ3実行記録: 文書と規約の定着

> [フェーズ3の計画](../drafting/03-foundation/01-readme-and-rules.md) を実行した詳細。正本の置き場は [完了記録](../complete/03-foundation/01-readme-and-rules.md) に要約済みである。

## 定着前に確認したこと

- 初回利用者は README の利用例から `add` と `list` を実行できた。
- 保存形式に依存する処理は追加と一覧の両方であり、片方だけの検証では破損を見逃す。デモで `## 午前` を含むファイルが一覧で落ちたのが実例。
- タグや検索に関する実例はまだなく、手順をスキル化する根拠はない。

## ユーザーレビューと反映

| レビュー結果                            | 反映先                                                     |
| --------------------------------------- | ---------------------------------------------------------- |
| README は目的を先に読みたい             | README の最初にツールの一文説明を置く                      |
| 保存形式変更時の検証は常時必要          | エージェント規約に検証すべき項目を一文で置く               |
| 項目の数を書くと増えたとき嘘になる      | 規約から「4つ」の数を削り、項目を列挙するだけにした        |
| 移行手順は今は不要                      | 設計文書・スキルを作らず、必要時に別計画で扱う             |

## 見送った提案: 「サブコマンド追加」スキル

作業エージェントが、次の内容のスキルを提案した。

> `worklog` にサブコマンドを追加するとき、入口の振り分け、保存・読込、テスト、README を順に更新する手順。

見送った理由:

- サブコマンドは `add` と `list` の2つで、後から追加した実績がない。
- 手順を今書くと、実際に追加したときの不具合を知らない推測の手順になる。
- 次にサブコマンドを足す計画が実際に走ったとき、手順が繰り返されるか確認してから作る。

## 重複を避けた配置

- 利用方法と検証入口を README に集約した。
- 不変条件だけをエージェント規約に置いた。
- 技術比較とデモ時の判断は repo-plans に残し、同じ説明を README や規約へ複製しなかった。
- `WORKLOG_DIR` の存在は、README ではなくテストの先頭コメントに一行だけ置いた。

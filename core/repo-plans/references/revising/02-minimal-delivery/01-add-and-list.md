# 最小実装と初回利用: `worklog` の `add` と `list`

> 記入例の時点: `revising`。[drafting](../../drafting/02-minimal-delivery/01-add-and-list.md) の計画で実装し、利用者へデモした後の改訂。デモで見つかった「手で直すと壊れる」問題の扱いに注目。次の時点は [complete](../../complete/02-minimal-delivery/01-add-and-list.md)。

## 目的と対象外

- 目的: `add` と `list` を実際に使える最小のコマンドとして動かし、日常の作業メモとして使えるかを利用者に確認してもらう。
- 対象外: 保存先指定、タグ、検索、編集、削除、配布（フェーズ1で合意）。

## 前提

- [フェーズ1の完了](../../complete/01-specification-and-technology/01-worklog-first-slice.md): 一日ごとの Markdown、Python 3.11 以上の標準ライブラリだけ、保存先は `~/.worklog/` 固定、一覧に作成時刻を表示する。
- 既存のルール・スキルは無い。

## 計画

### 実装範囲

- `add <本文>` が当日の Markdown ファイルへ `- HH:MM 本文` の一行を追記する。（変更なし）
- `list` は日付ごとの見出しの下に、時刻と本文を追加順に並べる。（デモ後に変更）
- 形式に合わない行（手で書き足した見出しなど）は、時刻なしでそのまま字下げして表示する。保存ファイルは書き換えない。（デモ後に追加）
- 保存データが無いときは「メモはまだありません」と表示し、終了コードを成功とする。
- 本文が空、または改行を含む場合は保存せず、終了コード 2 にする。

```console
$ worklog list
2026-09-15
  17:40  設計メモを共有
2026-09-16
  09:12  レビュー指摘を反映
  ## 午前
  14:32  認証APIの調査を完了
```

### 変更対象

作るファイル（これ以外は作らない）:

```text
worklog/
  README.md
  src/worklog/__main__.py   # 引数を受け取り add / list を振り分ける
  src/worklog/store.py      # 一日ごとの Markdown の追記と走査
  tests/test_store.py
  tests/test_cli.py
```

### 利用・検証の入口

- README に最小の利用例と検証コマンド `python -m unittest` を載せる。
- テストは時刻を外から差し込める形にし、日付またぎを再現する。

### 今回作らないもの

- 依存関係、設定ファイル、抽象化レイヤー、将来用のサブコマンド。

### 実装中に追加した計画外の事項

- テストが利用者の実データを書き換えないよう、保存先を環境変数 `WORKLOG_DIR` で差し替えられるようにした。テスト専用であり、利用者向けの「保存先指定」ではない。README には書かない。経緯は [progress/02-minimal-delivery.md](../../progress/02-minimal-delivery.md)。

## 完了条件と検証方法

- [x] 空データで `list` すると「メモはまだありません」を表示し、成功終了する（`python -m unittest`）。
- [x] 1件追加して `list` すると、作成時刻と本文を表示する（同上）。
- [ ] 日付をまたぐ複数件を、日付見出しの下に追加順で表示する（同上。見出しの確認を追加する）。
- [x] 空本文と改行入り本文は保存せず、終了コード 2 になる（同上）。
- [ ] 保存ファイルを手で直した内容が `list` に反映され、形式に合わない行があっても落ちない（`## 午前` を含むテストを追加し、再デモする）。
- [x] 日本語の本文を Windows と Mac の双方で読み書きできる（手動で確認）。

## ユーザーとの対話

### 質問（回答まで、その判断に依存する作業を進めない）

- なし。

### レビュー項目（作業後に確認してもらう）

- 日付見出しを含む一覧が、日報を書くときに読みやすいか。
- 手で直したファイル（`## 午前` を含む）の一覧表示で困らないか。

### 回答と反映

デモで見せた出力（自動テストは全件成功した後）:

```console
$ worklog list
2026-09-15 17:40  設計メモを共有
2026-09-16 09:12  レビュー指摘を反映
2026-09-16 14:32  認証APIの調査を完了
```

利用者からのフィードバック:

> 1. 日付が行ごとに繰り返されるので、日が変わった場所が目で追いにくい。日付は見出しにしてほしい。
> 2. 昨日のファイルをエディタで開いて、誤字を直したついでに、行の間へ「## 午前」と書いてしまった。そのあと `list` したらエラーで落ちた。直せる形式にしたのに、手で触ると壊れるのは困る。
> 3. 検索はまだ要らない。

| 受け取った内容                   | 採否と理由                                                                                                                                                                              | 変更した箇所       |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| 日付を見出しにしてほしい         | 採用。表示だけの変更で、保存形式と `add` は変えない。                                                                                                                                   | 実装範囲、完了条件 |
| 手で直すと `list` が落ちる       | 採用。フェーズ1で「人が直す」を要件にしたのに、形式外の行を読む挙動を決めていなかった（再現と原因は [progress](../../progress/02-minimal-delivery.md)）。形式外の行はそのまま表示する。 | 実装範囲、完了条件 |
| 検索はまだ要らない               | 確認。対象外のまま。                                                                                                                                                                    | なし               |
| （複数行のメモについて言及なし） | 一行一メモのまま。再デモで改めて確認する。                                                                                                                                              | なし               |

## 未決事項と引継ぎ

- ルール候補: 「保存形式を使う処理は、人が手で直した内容も読めなければならない」は、保存形式を変えるたびに効く不変条件である。フェーズ3で正本の置き場を決める。
- 日付見出しの追加は単発の表示調整であり、計画と progress にだけ残す。

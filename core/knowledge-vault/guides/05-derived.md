# 派生物: 一覧・索引・閲覧画面・派生文書

正本（`vault/` の Markdown）だけを更新すれば、ほかはすべて追随する形にする。派生物は直接編集せず、消しても作り直せるようにしておく。

| 派生物                              | 作る道具             | 作り直すタイミング                                                   |
| ----------------------------------- | -------------------- | -------------------------------------------------------------------- |
| ダッシュボードの一覧                | `build_dashboard.py` | vault を書いた後に毎回                                               |
| スキーマ一覧 `docs/vault-schema.md` | `gen_schema_doc.py`  | `schema.py` を変えたとき（commit フックで差分検査）                  |
| 検索索引 `data/vault_index.sqlite`  | `build_index.py`     | 読む側が `ensure_index()` を呼ぶと、正本が変わっていたときだけ自動で |

## ダッシュボード: 生成区間と手書き区間を分ける

`dashboard.md` のうち、マーカー `<!-- dashboard:begin -->` 〜 `<!-- dashboard:end -->` の間だけを frontmatter から生成し、マーカーの外（今のフェーズ・メモ・方針）は手書きで残す。

- 全部を生成にすると、人間の考え（「今月はここに集中する」）を書く場所が無くなる。
- 全部を手書きにすると、一覧が必ず古くなる。

生成区間の先頭に「手で編集しない」というコメントを入れ、生成元のスクリプト名を書いておく。

生成区間には「要対応 / 予定 / 待ち」「最近の出来事」「進行中の一覧」を並べる。

- **最近の出来事**: 直近 `RECENT_DAYS` 日のイベントログを新しい順に出す。frontmatter の直近アクション（これから）に対して、こちらは「最近何があったか」。AI が会話の最初にダッシュボードを読めば、ファイルを開き回らずに近況が分かる。
- **題材固有の列と小見出し**: 進行中の一覧に足す列（費用・適合度など）は `schema.py` の `DASHBOARD_COLUMNS`、小見出しで分ける enum のキーは `DASHBOARD_GROUP_BY` に書く。生成スクリプトは題材を知らない。

## 検索索引: SQLite を派生キャッシュとして使う

件数が増えると、`grep` で全ファイルを舐めるのは遅く、AI がファイルを片端から開くのはトークンの無駄になる。そこで正本から SQLite の索引を作り、検索はそこで行ってヒットした**正本のパス**を返す。

- **毎回全件作り直す**。差分更新はしない。数千件程度なら一瞬で終わり、整合性の心配が無い。
- **一時ファイルに書いてから `os.replace` で差し替える**。読み手が作りかけの DB を読むことが無い（Windows では読み手が開いていると置き換えに失敗することがあるので、数回リトライする）。
- **鮮度は指紋で判定する**。正本ファイルの件数と最終更新時刻（とテーブル構成のバージョン）を索引に記録し、変わっていたら作り直す。
- **全文検索は FTS5 の trigram トークナイザ**。日本語でも分かち書き辞書が要らない。3文字未満の語にはヒットしないので、その場合は LIKE にフォールバックする。
- **frontmatter 全体を JSON で持たせる**。よく使う値（種別・scope・status・更新日）は列にし、それ以外は `json_extract` で引ける。
- **外部スナップショット（`data/`）も同じ索引に入れる**。正本と区別できるよう種別を `snapshot` にする。
- **frontmatter の文字列値も全文検索に入れる**。`digests` の要約や台帳の `reason` は本文ではなく frontmatter にあるので、入れないと畳んだ情報が検索で見つからなくなる。
- **キーワードなしの絞り込みも引けるようにする**（`--kind`・`--scope`・`--tag`・`--where KEY=VALUE`・`--since`）。結果は日付の新しい順。イベントログは親エンティティのタグ・値でも一致させる（イベント1件ずつに分類を書かせないため）。
- 索引は git 管理外（`.gitignore`）。

規模がさらに大きくなり、言い換えや意味での検索が必要になったら、ベクトル検索を同じ派生キャッシュとして足す。正本は Markdown のまま変えない。

## 閲覧画面（任意）

人間が一覧で絞り込み・閲覧したくなったら、ローカルの Web 画面を作る。サンプルには含めていないが、作るなら次を守る。

- **読み取り専用**。正本を書き換えるのは AI / CLI だけ。画面から書けると、検証を通らない変更や、AI の知らない変更が生まれる。書き込みに当たる操作は「索引の作り直し」だけにする。
- **データは索引とローダーからだけ取る**。画面側で frontmatter を独自にパースしない。
- **127.0.0.1 だけで待ち受ける**。
- **`visibility: internal` のファイルは表示しない**。本文中の相対リンクは画面内の URL に変換し、変換できないリンクは無効にする。
- 本文の Markdown は HTML を無効にしてレンダリングする。JS は CDN から読まず同梱する。
- ラベル・並び順は `schema.py` から引き、テンプレートに値を書き写さない。

役割分担は「AI は CLI で検索・取得・記録、人間は画面で絞り込み・閲覧」。

## 派生文書（翻訳・要約）

ある正本から作った別の版（英訳、外部向けの要約など）には、frontmatter に次を持たせる。

- `source_file`: 派生元のパス（リポジトリルート相対）
- `source_updated_at`: 同期した時点の派生元の `updated_at`

派生元の `updated_at` の方が新しければ、検証が「同期漏れ」として警告する。正本を先に直し、派生側を同期してから `source_updated_at` を合わせる。`internal` のファイルは派生させない。

## リポジトリを公開する場合

道具（`tools/`・ルール・雛形）は公開し、データは公開しないなら:

- **非公開リポジトリを正本にする**。公開リポジトリへは CI で同期する。
- **ホワイトリスト方式**で公開するフォルダだけを選ぶ（`vault/`・`data/`・下書きのプランなどは対象外）。ブラックリスト方式だと、新しく作った個人フォルダが漏れる。
- **公開側は履歴を持たない単一コミットで force push する**。過去のコミットに個人情報が残らない。
- 公開側には、`vault/` と同じ構成の空の雛形（このテンプレートの `references/vault/` のようなもの）を置く。雛形も同じ検証を通す（`validate.py --root <雛形のルート>`）。

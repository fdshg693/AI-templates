# ライフサイクル: 着手から圧縮まで

1つの対象が記録されてから台帳に畳まれるまでの流れと、各段階で何を書くか。

```
check_entity ──NOT FOUND──▶ 公開情報で足切り? ──yes──▶ triage/ にバッチで記録
     │                              │no
     │                              ▼
     │                     entities/{key}/index.md を作る（status: researching）
     │                              │  調査・打ち合わせ・試用 → イベントログ ＋ index.md 更新
     │                              ▼
     │                     status を進める / 終了（adopted・dropped・blocked・blacklisted）
     │                              │  14 日以上経過・本人が承認
     │                              ▼
     │                     archive.md に数行で畳み、フォルダは git rm
     │
     │   （続いている対象は終わらないので、古いイベントログだけを index.md の digests に畳む）
     │
     ├─EXISTING──▶ 既存 index.md に「### 追記: YYYY-MM-DD」
     ├─OTHER SCOPE──▶ 参考提示して、この scope の条件で改めて判断
     └─EXCLUDED──▶ 過去の理由・再検討の条件を示して止める
```

## ステータスにメタデータを持たせる

ステータスは値だけでなく、**分類・並び順・除外範囲・ラベル・説明**を1か所（`schema.py` の `ENTITY_STATUS`）に持たせる。

| 持たせるもの                               | 使う場所                                             |
| ------------------------------------------ | ---------------------------------------------------- |
| 分類（active / closed / excluded）         | ダッシュボードの「進行中」の抽出、期限切れ警告の対象 |
| 並び順                                     | ダッシュボードで進んでいるものを先に                 |
| 除外範囲（none / same_scope / all_scopes） | 重複チェックの判定                                   |
| ラベル・説明                               | 一覧の表示、生成文書                                 |

読む側が `if status in ("dropped", "blocked")` のように値を並べると、ステータスを足したときに全部直す必要がある。分類で書けば `schema.py` の1行で済む。

「自分が決めて終わった（dropped）」と「外部要因で終わった（blocked）」のように、**誰が決めたか**で終了状態を分けておくと、後から振り返るときに役立つ。迷ったら本人に確認する。

## 追記で育てる

- 同じ対象への再相談は新しいファイルを作らず、`index.md` に `### 追記: YYYY-MM-DD` で足す。
- ただし frontmatter と「4. 結論・所見」は常に最新に書き換える（古い結論を残すと、上から読んだときに誤解する）。経緯は追記、現状は上書き、と役割を分ける。
- 1回の出来事（打ち合わせ・試用・レビュー）はイベントログに書き、`index.md` には要点とリンクだけを足す。イベントログは書いた時点のまま残し、後から書き換えない（`result` だけは結果が出たら更新する）。

## 直近アクションを frontmatter で追う

`action_type`・`next_action`・`next_due` を書いておくと、ダッシュボードの先頭に「要対応 / 予定 / 待ち」として集まり、期限切れは検証が警告する。

| `action_type`     | 意味                 | 並び         |
| ----------------- | -------------------- | ------------ |
| `action_required` | 自分側の対応が必要   | 期限の近い順 |
| `scheduled`       | 日時が確定した予定   | 日時の近い順 |
| `waiting`         | 相手の返信・結果待ち | 期限の近い順 |
| `none`            | タスクなし（既定）   | —            |

「次に何をするか」を本文の奥に書くと、件数が増えたときに埋もれる。frontmatter にあれば一覧に浮き上がる。

## 重複・除外チェック

`check_entity.py` は名称・キー・別名を正規化（Unicode 正規化・小文字化・空白と記号の除去）して照合する。表記ゆれ（「Acme Notes」「AcmeNotes」「アクメノート」）は `aliases` に書いておく。

| 照合先               | 由来の status                | 除外範囲                     |
| -------------------- | ---------------------------- | ---------------------------- |
| 生きたフォルダ       | その frontmatter の `status` | ステータスのメタデータに従う |
| triage の `entries`  | `discarded`                  | 同じ scope                   |
| archive の `entries` | 元の `status`                | ステータスのメタデータに従う |

部分一致しかしなかったものは「似た名前」として示すだけにし、除外と判定しない。

## 圧縮（見送り台帳）

終了したフォルダを置きっぱなしにすると、検索結果と AI の文脈が古い情報で埋まる。そこで一定期間（既定 14 日）を過ぎたら台帳に畳む。

- **すぐには畳まない**: 終了直後は振り返りや再提案で詳細を見直すことがある。
- **定期実行しない**: 相談や整理のついでに `compact.py list` で候補を出し、どれを畳むかは本人が決める。
- **本質だけ残す**: `reason`（何が合わなかったか）を**条件の言葉で** 1〜2 文、`reconsider_if`（何が変われば再検討するか）を書く。対象の説明や経緯は書かない。再相談のとき「その条件が今も変わっていないか」を確かめるだけで判断できるようにするため。`reason` には文字数上限を設けて、長文化を機械的に防ぐ。
- **AI が書き、本人が確認する**: `close_reason` を写すだけにせず、イベントログまで読んで本当の理由を拾う。CLI は下書きと機械的な追記・削除だけを担う。
- **詳細は git に任せる**: フォルダは `git rm` する。未コミットの変更があるフォルダは畳めないようにして、履歴に残らない変更を消さない。
- **学びを台帳に閉じ込めない**: 畳むたびに「この見送りで初めて分かった条件・好み」が無いか確かめ、あれば `profile/` や `criteria.md` に追記する。
- **再検討するとき**: 台帳のエントリを消してから新しいフォルダを作り、`index.md` の冒頭に台帳の要約を引き写す。台帳と生きたフォルダに同じキーがあると検証エラーになる（どちらが正か曖昧になるため）。
- **参照は書き換えない**: コンタクトの `introduced` のキーは、台帳のキーでも解決できるので、畳んでも書き換えない。

## 続いている対象の古いイベントを要約に畳む（digests）

台帳への圧縮は「終わった対象」だけが相手なので、使い続けているツールや続けている習慣のように**終わらない対象**は、イベントログが増え続ける。古いログで検索結果と AI の文脈が埋まり、直近の動きが見えにくくなる。そこで一定期間（`schema.py` の `EVENT_DIGEST_DAYS`）より前のイベントログは、その対象の `index.md` の frontmatter `digests` に「期間・件数・その期間の傾向」の1エントリとして畳む。

- **直近は一次情報、昔は傾向**: 期間内のログは書いた時点のまま残し、期間を過ぎたものだけを畳む。「最近どうしているか」はイベントログ、「以前はどうだったか」は `digests` を読めば分かる。
- **期間ごとにまとめる**: 1回の圧縮で、その対象の期間を過ぎたログを全部1エントリにする。エントリは古い順に並ぶ。
- **AI が書き、本人が確認する**: `summary` は件数や日付の羅列ではなく「何が分かったか・どう変わったか」を 2〜3 文で書く（上限 `DIGEST_SUMMARY_MAX`）。CLI は期間と件数の下書き、frontmatter への追記、`git rm` だけを担う。
- **本文のリンクを外す**: 畳んだログへの本文のリンク（「経過サマリ」など）は切れる。要点が `digests` に入ったので、本文からはリンクを外す。残っていると検証が警告する。畳んだ期間のログが残っている場合も警告する（二重になるため）。
- **変わりにくい傾向は profile へ**: 畳むたびに、期間をまたいで繰り返し出てきた好み・習慣・条件が無いか確かめ、あれば `profile/` に書く。`digests` は「その対象の経緯」、`profile/` は「対象をまたいで変わりにくい本人の傾向」。
- **台帳に畳む対象は除く**: `ARCHIVABLE_STATUS` の対象は、フォルダごと台帳に畳む方で扱う。
- 定期実行しない・未コミットの変更があれば拒否する・詳細は git に任せる、は台帳と同じ。

## 判断軸の能動的な更新

記録は「対象の情報を貯める」だけで終わらせない。調査・打ち合わせのたびに、AI は本人に質問して、まだ書かれていない好みや条件を引き出す（例: 「ゲストに見せるページを1枚ずつ選べないと困るか？」）。答えは `profile/` か `criteria.md` に日付付きで追記し、`index.md` の「3. 判断軸の確認・更新」に何を反映したかを残す。判断軸が育つほど、次の対象の足切りと評価が速く正確になる。

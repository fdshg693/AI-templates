# 核となる原則

このテンプレートは「何かを継続的に調べ・比較し・判断していく活動」の記録を、**数か月〜数年、数百〜数千件**の規模になっても AI と人間の両方が迷わず使える状態に保つための仕組み。題材（ツール選定、物件探し、論文調査、取引先管理、趣味の収集…）は問わない。

少量・短期なら、メモアプリに書き散らしても困らない。困り始めるのは次のようなとき。

- 同じ対象を、前に調べたことを忘れてもう一度調べている
- 「今どうなっているか」を知るのに、何十ファイルも開く必要がある
- 書いた本人も AI も、ある値が「確かめた事実」なのか「推測」なのか分からない
- 終わった案件のファイルが積み上がり、検索結果が古い情報で埋まる
- 書式がファイルごとに少しずつ違い、機械的に集計できない

以下の原則は、それぞれこのどれかへの対策になっている。

## 1. 正本は1か所。データと道具とキャッシュを分ける

情報の正本（SSOT）は frontmatter 付き Markdown として `vault/` にだけ置く。

| 置き場所                                                                | 何か                               | 失ったら     |
| ----------------------------------------------------------------------- | ---------------------------------- | ------------ |
| `vault/`                                                                | 正本。判断・経緯・評価             | 取り返せない |
| `data/`                                                                 | 外部から取ってきたスナップショット | 取り直せる   |
| `data/vault_index.sqlite`、`docs/vault-schema.md`、ダッシュボードの一覧 | 正本から作る派生物                 | 作り直せる   |
| `tools/`                                                                | スキーマと CLI                     | コード       |

「どれが正本か」が決まっていると、食い違ったときに迷わない。派生物は直接編集しないので、いつ消しても作り直せる。外部のスナップショットに判断を書き込まないので、取り直しても判断が消えない。

## 2. 1件1フォルダ、1回1ファイル、状態はフォルダではなく frontmatter に

- 調べる対象（エンティティ）ごとに1フォルダ。`index.md` が最新の要約。
- 打ち合わせ・試用など、その対象について起きた出来事は1回1ファイル（`{YYYY-MM-DD}_{kind}.md`）で同じフォルダに置く。
- 状態（調査中・見送り・採用…）は frontmatter の `status` だけで表し、状態が変わってもフォルダを移動しない。

フォルダで状態を表すと、移動のたびにリンクが切れ、履歴が追いにくくなり、「移動し忘れ」と「frontmatter の書き忘れ」の二重管理になる。パスが一生変わらなければ、どこからでも安心してリンクできる。

## 3. スキーマをコードに1か所だけ書き、機械で検証する

frontmatter のキー・型・許容値・配置パスは `tools/vault/schema.py` にだけ書く。一覧文書はそこから生成し、検証 CLI を commit 前に必ず通す。

人間も AI も、書式のルールを毎回正しく覚えてはいられない。ルールが文章にしか無いと、件数が増えるほど少しずつ崩れ、気づいたときには集計も検索も信用できなくなる。**検証できないルールは、長期的には守られない**前提で設計する。

詳しくは [03-schema.md](03-schema.md)。

## 4. 絞り込みに使う値は構造化し、補足は文章で分ける

金額は単位を揃えた整数、分類は enum、日付は `YYYY-MM-DD`。補足は `*_note` の自由文に分ける。

「月 5,000 円くらい（年払いなら割引）」を1つの欄に書くと、人間には読めても「月 1 万円以下」で絞り込めない。機械が扱う値と人間が読む説明を最初から分けておけば、件数が増えても一覧・フィルタ・並べ替えが効く。

## 5. 確かさを記録する（事実と推測を分け、評価は幅で持つ）

- どこまで確かめたか（`evidence_level`）、確認できたこと（`verified_items`）、未検証のこと（`unverified_items`）を書く。
- 評価スコアは `score_min` / `score_max` の幅で持ち、確かめるほど幅を狭める。

公開情報やカタログは、都合の悪いことを書かない。そこからの判断に「85 点」と断定的な数字を付けると、後から読んだ人（未来の自分や AI）はそれを確かめた結論だと誤解する。幅と根拠が残っていれば、どこを確かめれば判断が固まるかが分かる。

## 6. 追記で育て、終わったものは本質だけ残して畳む

- 同じ対象の再相談は新しいファイルを作らず、既存の `index.md` に日付付きの見出しで追記する。
- 終わった対象は一定期間後に、台帳（`archive.md`）へ「何が合わなかったか」「何が変われば再検討するか」の数行だけ残して畳み、元のフォルダは消す。詳細は git の履歴にある。

消さずに積み上げ続けると、検索結果が終わった案件で埋まり、AI が読む文脈も膨らむ。逆に跡形もなく消すと、同じものをまた調べてしまう。**判断に必要な本質だけを小さく残す**のが長期運用の要。詳しくは [04-lifecycle.md](04-lifecycle.md)。

## 7. 新しく扱う前に、必ず既存の記録と照合する

新しい対象に着手する前に、名称と別名を正規化して、生きているフォルダ・打ち切りログ・台帳と照合する（`check_entity.py`）。

件数が増えると、記憶に頼った「たぶん初めて」は外れる。照合を手順に組み込んでおけば、見送った理由をすぐに示せ、再調査のコストを払わずに済む。

## 8. 区分（scope）で同じ構造を並べ、判断の範囲を区切る

条件がまったく違う活動（例: 業務用と個人用）は `vault/scopes/{scope}/` に分け、同じ構造を並列に持たせる。共通の判断軸は `profile/` に置く。

条件を混ぜると、ある区分での「見送り」が別区分の判断を縛ってしまう。除外判定も scope の中だけで効かせ、別 scope の記録は参考提示にとどめる。迷う記述は scope 側に置く（後から共通化する方が安全）。

## 9. 一覧・索引・閲覧画面は派生物として自動生成する

- ダッシュボードの一覧はマーカー区間だけを frontmatter から生成し、マーカーの外は手書きで残す。
- 横断検索は正本から作り直せる SQLite 索引（全文検索つき）で行う。
- 人間向けの閲覧画面を作るなら読み取り専用にし、書き込みは AI / CLI だけが行う。

手で保守する一覧は必ず古くなる。正本だけを更新すれば一覧も検索も追随する形にしておけば、更新し忘れが起きない。詳しくは [05-derived.md](05-derived.md)。

## 10. AI と組む前提で、機械にさせることと判断させることを分ける

- CLI は stdout にファイルパスだけを返し、AI はそのパスを開いて読む（余計な出力でトークンを使わない）。
- CLI は候補の列挙・下書き・機械的な変更だけを担い、「なぜ見送るか」のような判断は AI が材料を読んで書き、本人が確認する。
- 機械的なフィルタ（キーワード・スコア）は粗い事前フィルタとして使い、それだけで結論を出さない。
- AI は記録のたびに本人へ質問し、まだ書かれていない判断軸を引き出して `profile/` に追記する。

詳しくは [06-ai-collaboration.md](06-ai-collaboration.md)。

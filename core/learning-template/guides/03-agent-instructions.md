# AI向け指示ファイル（AGENTS.md）の書き方

[01-philosophy.md](./01-philosophy.md) の原則3・4を、実際のファイル構成に落とし込む。

## 1. 正本とエイリアスの関係

- `AGENTS.md` を正本にする。ルール・方針の文章は必ずここに書く。
- `CLAUDE.md`（や他のAIツールが読む規約ファイル）は、中身を **`@./AGENTS.md` の1行だけ** にする。
- この関係は**リポジトリ内の全階層**（ルート／トップフォルダ／トピック）で繰り返す。プロジェクト
  （ステップ）単体の階層には基本的に置かない（後述）。

`@./` は「このファイルと同じディレクトリの」を意味する Claude Code の import 記法。**`@` import は
`CLAUDE.md` 側だけで使い、`AGENTS.md` には書かない。** `AGENTS.md` は Claude Code 以外のツールも読む正本なので、
`@` を解釈しないツールでは文字列として扱われ、参照先の内容が届かない。`AGENTS.md` から他のファイル
（`README.md` 等）を参照するときは、通常の Markdown リンクにするか、必要な要約を直接書く。

## 2. 階層ごとに書く内容を変える

### ルート `AGENTS.md`

リポジトリ全体に共通するルールを書く。最低限含めるべき項目：

- **採用ツール方針**（言語・パッケージマネージャ・IaCツール等、迷ったときのデフォルト選択）
- **コード品質の基準**（コメントの付け方、設定値の取得方法など）
- **ガードレール**（AIが勝手にやってよいこと／やってはいけないこと。特に「実際の環境へのデプロイ・
  課金の発生する操作」は明示的な指示がない限り行わない、といった安全側のルール）
- **各プロジェクト共通のファイル構成**（後述の「プロジェクト（ステップ）階層」を参照）
- **ドキュメント管理ルール**（後述の3ファイル分割ルールへの言及）
- **進め方の指示**（例: 「サブフォルダは独立しているので、関連プロジェクト範囲外は無関係に検索・確認しない」
  といった、AIの探索範囲を無駄に広げさせないための指示）

具体例は [`references/AGENTS.md`](../references/AGENTS.md)。

### トピック階層（`study/{topic}/AGENTS.md` 等）

トピックが浅いうちは `AGENTS.md` 1枚に、次の3つをまとめて書く。

- プロジェクト早見表（1プロジェクト1〜2行、フォルダへのリンク付き）
- 学習済みの概念（まとめて記載。個々のプロジェクトの実装経緯までは書かない）
- まだ触れていない主要概念（次に何を作るかの目安）

**トピックが深まり、このファイルが長くなってきたら3ファイルに分割する**（分割前と同じ内容を
探すときの基準は「経緯・対比・実験手順まで書きたくなったか」）。

- `AGENTS.md` … 上記3点に絞った**現状把握用の早見表**のみ残す
- `HISTORY.md` … 各プロジェクトの詳細（「何を解く問題としたか」「前のプロジェクトと何が変わったか」
  「どう実装したか」「どんな設定の出し入れで因果を確かめたか」）を溜める
- `PLAN.md` … この先のプロジェクト候補・学ぶ概念・依存関係・進め方のロードマップ（実装詳細には踏み込まない）

`AGENTS.md` / `HISTORY.md` / `PLAN.md` を、**現状まとめ・経緯記録・今後の計画という役割で分ける**。
具体例は [`references/study/{topic}/AGENTS.md`](../references/study/{topic}/AGENTS.md) と
[`PLAN.md`](../references/study/{topic}/PLAN.md)。

トップフォルダ階層（`study/AGENTS.md`）には、各トピックの到達点を1〜2行ずつ並べた一覧を置く
（例: [`references/study/AGENTS.md`](../references/study/AGENTS.md)）。

### プロジェクト（ステップ）階層

個々のプロジェクトフォルダ（例: `study/{topic}/{project}/`）には、通常 `AGENTS.md`／`CLAUDE.md` を
**置かない**。ルール自体はルートの `AGENTS.md` にある「各プロジェクト共通ファイル構成」で
一括して定義し、各プロジェクトはそれに従うだけにする。共通ファイル構成の目安：

- `README.md` … このプロジェクトで行う内容・手順・学習の流れ
- `KNOWLEDGE.md` … このプロジェクトで新たに出た用語・概念（前のプロジェクトでカバー済みの語は含めない）
- `PLAN.md`（任意）… そのプロジェクト固有の設計。大きめのプロジェクトかつ明示的に必要な場合のみ
- `MERMAID.md`（任意）… 構成やフローを図で表現したい場合
- `questions/`（任意）… 学習中に出た質問を、単なるQ&Aでなく学ぶべき内容の整理として体系化する場所
- 実行コマンドをまとめる `justfile`（複雑になったら可読性重視で `Taskfile.yml` に切り替える）

細かく分ければよいわけではなく、**可読性・理解しやすさを最優先に分割する**。

## 3. 「進め方」の指示を忘れない

AGENTS.md には、ファイル構成のルールだけでなく、AIがリポジトリ内をどう探索すべきかも書く。
サブフォルダ（トピック・プロジェクト）は基本的に独立しているため、次のような指示が効く。

- 今回関連するプロジェクト範囲内に検索を絞り、無関係なプロジェクトの内容を確認しない
- 関連プロジェクト外を確認する場合も、README等で概要を把握する程度に留める

これがないと、AIが1つの変更のために無関係な学習履歴まで大量に読み込み、コンテキストと時間を浪費する。

## 4. 「バグらせない」ための注意

このパターンの弱点は、**索引ファイル（AGENTS.md／README.md）の内容と実態が乖離しやすい**こと。
特に次のミスが起きやすいので、AGENTS.md のルールとして明示しておくとよい。

- あるフォルダ用に書いた索引を別フォルダにコピーしたまま、フォルダの実際の役割に合わせて
  書き換え忘れる（コピー元の内容がそのまま残り、実態と矛盾する）
- トピックが増えたのに、上位階層の索引（例: ルート README.md やトップフォルダの AGENTS.md）を
  更新し忘れる
- 「学習記録」用のフォルダ（`study/` 等）と「操作リファレンス」用のフォルダ（`cheatsheet/` 等）の
  役割が曖昧になり、同じ内容が両方に書かれる

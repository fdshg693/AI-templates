# 判断を書く

あとから「なぜこうなっているのか」と聞かれそうな設計判断をしたとき、またはその判断を提案するときに読む。既存の判断を覆すときは [superseding.md](superseding.md) も読む。

## 書く対象

次のどれかに当てはまる判断を1件＝1ファイルで書く。当てはまらないものは書かない（数が増えると読まれなくなるため）。

- 後から戻すのに1日以上の作業がかかる（データ形式、永続化方式、外部サービス、公開 API の形）
- 複数のフォルダ・モジュールの書き方を縛る（エラー処理の方針、命名規約、依存ライブラリの選定）
- 検討して**採用しなかった**ことを残さないと、同じ提案が繰り返される

実装の手順・作業の分割は書かない（それは実装計画の役割。判断ファイルには結論と理由だけを置く）。

## 作るもの

### ファイル名

`NNNN-{slug}.md`。`NNNN` は4桁の連番で、既存の最大番号＋1（`uv run decisions/lint_decisions.py decisions --next` で表示できる）。`{slug}` は判断内容を表す英小文字とハイフン。番号は欠番になっても詰めない（他の場所から番号で参照されるため）。

### frontmatter

```yaml
---
type: Decision
status: proposed
date: 2026-10-20
supersedes: []
superseded_by: []
---
```

| キー            | 値                                                                    |
| --------------- | --------------------------------------------------------------------- |
| `type`          | `Decision` 固定                                                       |
| `status`        | 下の状態表の値のどれか                                                |
| `date`          | `YYYY-MM-DD`。最後に `status` を変えた日                              |
| `supersedes`    | この判断が置き換える判断の番号のリスト（例: `[0002]`）。無ければ `[]` |
| `superseded_by` | この判断を置き換えた判断の番号のリスト。無ければ `[]`                 |

状態（`lint_decisions.py` の `STATUSES` と同期）:

| `status`     | 意味                                                 | 次に取りうる状態        |
| ------------ | ---------------------------------------------------- | ----------------------- |
| `proposed`   | 提案中。まだ従わなくてよい                           | `accepted` / `rejected` |
| `accepted`   | 採用済み。リポジトリはこれに従う                     | `superseded`            |
| `rejected`   | 検討の結果、採用しなかった                           | なし                    |
| `superseded` | 後の判断に置き換えられた。`superseded_by` を必ず書く | なし                    |

### 本文の節

次の `##` 見出しをこの順で置く（`lint_decisions.py` の `SECTIONS` と同期）。最初の `#` 見出しは「`NNNN` 判断の要約」。

| 見出し              | 書くこと                                                                                            |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| `## 背景`           | 判断が必要になった状況と制約。数値・期限など確かめられる事実で書く                                  |
| `## 決定`           | 採ることにした（`rejected` なら、採らないことにした）結論を1〜3文。「〜する」「〜しない」で言い切る |
| `## 検討した選択肢` | 選択肢ごとに `###` 見出しと、利点・欠点の箇条書き。採用案も含めて2つ以上                            |
| `## 結果`           | この判断で起きること。楽になること・難しくなること・後で見直す条件                                  |

## 手順

1. 既存の判断ファイルの `#` 見出しを一覧し、同じ論点の判断が無いか確かめる。`accepted` の判断を覆す内容なら [superseding.md](superseding.md) に切り替える。
2. `--next` で番号を決め、`status: proposed` でファイルを作る。
3. 4つの節を書く。`## 検討した選択肢` は採用しない案の欠点だけでなく利点も書く（後で状況が変わったとき再評価できるように）。
4. lint を実行し、エラー0にする。
5. 判断の持ち主（導入先の `AGENTS.md`「導入先固有の運用」に書かれた人。無ければ依頼者）に結論を確認してもらう。
6. 確認結果に応じて `status` を `accepted` か `rejected` に変え、`date` を更新する。`rejected` のときは `## 決定` を「〜しない」に書き直してよい。

## 完了条件

- [ ] ファイル名が `NNNN-{slug}.md` で、番号が既存と重複していない
- [ ] `status` が `accepted` か `rejected`（確認待ちなら `proposed` のまま報告する）
- [ ] 4つの節がそろい、`## 検討した選択肢` に2つ以上の `###` がある
- [ ] lint がエラー0で終わる

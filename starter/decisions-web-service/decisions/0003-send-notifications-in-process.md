# 0003 通知は API サーバー内でレスポンス後に送る

## 背景

メール通知とチャット通知を追加することになった。通知の送信は外部サービスの応答待ちで1件あたり最大5秒かかり、API のリクエスト処理の中で送ると画面の応答が遅くなる。新しく入ったメンバーから、通知部分を独立したサービスにする提案があった。運用担当はいない（[0002](0002-store-data-in-sqlite.md) の背景）。

## 決定

通知機能は別サービスに分割せず、API サーバー内で FastAPI の BackgroundTasks を使い、レスポンスを返した後に送る。

## 検討した選択肢

### API サーバー内でレスポンス後に送る

- 利点: 追加のサーバーが要らない。数行で書ける
- 欠点: サーバー再起動・異常終了の瞬間に送信中の通知が失われる。失敗した送信を後から再実行できない

### 通知を別サービスに分割する

- 利点: 通知の障害が API に波及しない。通知部分だけを別の頻度でデプロイできる
- 欠点: デプロイ対象とサーバーが2倍になる。運用担当がいない現状では監視の手が回らない

### リクエスト処理の中で同期的に送る

- 利点: 送信の成否をそのまま利用者に返せる
- 欠点: 応答が最大5秒遅れる

## 結果

- 通知の送信で画面の応答が遅れない
- 送信処理の例外はすべて記録して握りつぶし、API の応答に影響させない
- 再起動などで失われた通知の指摘が月1件を超えたら見直す。運用担当が置かれたら、別サービスへの分割をもう一度提案してよい

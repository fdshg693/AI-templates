# 0008 バックグラウンドジョブは PostgreSQL のテーブルをキューにして処理する

## 背景

[0003](0003-send-notifications-in-process.md) で、通知はレスポンス後に API サーバー内で送ることにした。その後、再起動時に失われた通知の指摘が10月だけで3件あり、0003 の「月1件を超えたら見直す」に当たった。[0006](0006-move-to-postgresql-with-uuid.md) で PostgreSQL が使えるようになったため、追加のサーバー無しで永続的なキューを持てる。運用担当はまだいない。

## 決定

通知などのバックグラウンドジョブは別サービスに分割せず、PostgreSQL の `jobs` テーブルに登録し、API サーバーとは別プロセスのワーカーが `SELECT ... FOR UPDATE SKIP LOCKED` で取り出して処理する。ワーカーは API サーバーと同じリポジトリ・同じイメージで動かす。送信処理の例外は記録したうえでジョブを失敗状態にし、API の応答には影響させない。

## 検討した選択肢

### PostgreSQL のテーブルをキューにする

- 利点: 追加のサーバーが要らない。ジョブの登録を業務データの更新と同じトランザクションにできる
- 欠点: 毎秒数百件を超えるとデータベースの負荷になる。リトライや遅延実行を自前で書く必要がある

### Redis ＋ キューライブラリ

- 利点: リトライ・遅延実行・監視画面がライブラリにそろっている
- 欠点: Redis の運用が増える。業務データとジョブ登録を同じトランザクションにできない

### 0003 の方式のまま、再起動前に送信完了を待つ

- 利点: 実装の変更が小さい
- 欠点: 異常終了時には効かない。送信の失敗をあとから再実行できない

## 結果

- 再起動・異常終了で通知が失われなくなる
- ワーカーのプロセス監視が増える。ジョブが10分以上滞留したら通知する監視を足す
- ジョブ量が毎秒100件を超えたら、専用のキューへの移行を別の判断として検討する

# 0006 PostgreSQL に移行し、ID を UUID v7 にする

## 背景

[0002](0002-store-data-in-sqlite.md) は「利用チームが3つ以上になる、または書き込み待ちによるタイムアウトが週1回以上出たら見直す」としていた。10月時点で利用チームは5つになり、9月最終週には書き込み待ちのタイムアウトが4回出た。冗長化のため API サーバーを2台にする必要もある。

移行ではデータを新しいデータベースへ流し込むため、[0004](0004-use-integer-ids.md) の連番 ID を保つには移行中の書き込みを止める必要がある。また、外部チームへ API を公開する予定が決まり、連番 ID から件数が推測されることが問題になった。

## 決定

データはマネージド PostgreSQL に移し、新しく作るリソースの ID は UUID v7 にする。既存の整数 ID は `legacy_id` 列に残し、旧 URL（`/tasks/42`）は新 URL へ 301 で転送する。スキーマ変更はマイグレーションファイルで行い、手作業で SQL を流さない。

## 検討した選択肢

### PostgreSQL ＋ UUID v7

- 利点: 同時書き込みとサーバーの複数台化に対応できる。UUID v7 は生成順に並ぶため索引の効率が落ちにくく、件数も推測できない
- 欠点: 月額費用がかかる。URL が長くなり、旧 URL の転送を当面保守する必要がある

### PostgreSQL ＋ 連番整数のまま

- 利点: URL が変わらない
- 欠点: 移行中に書き込みを止める必要がある。公開 API で件数が推測される問題が残る

### SQLite のまま WAL モードにする

- 利点: 移行作業が要らない
- 欠点: 書き込み待ちは減るが、サーバーの複数台化はできない

## 結果

- API サーバーを2台にできる
- 旧 URL の転送を、アクセスが月100件を下回るまで保守する
- スキーマを変える作業は、マイグレーションファイルの追加とレビューが必須になる

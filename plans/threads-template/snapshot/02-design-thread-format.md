# Step 2: 要件の合意とスレッド書式の確定

> [00-overview.md](00-overview.md) の続き。template-create 手順1（要件を固める）に相当する。決めた内容は Step 3・4 の本文へ反映し、ガイドの正本は Step 3 で書く。

## やること

template-create 手順1の5点（目的と対象外／コピー先／場面一覧／成果物一覧／不変条件）を以下の素案をもとにユーザーへ提示して合意し、スレッドの書式・状態値・プランとの連携ルールを確定する。

### 素案

- **目的と対象外**: 複数プランにまたがる変更・手戻り・仕様変更の経緯を束ねる。1プランで閉じる作業は plans だけで扱い、スレッドを立てない（基準は「プランが2つ以上」または「完了済みプランへの手戻りが発生した」）。設計判断そのものの記録は `core/decisions`、新規リポジトリ立ち上げは `core/repo-plans` の範囲で、スレッドからはリンクするだけにする。
- **コピー先**: 導入先の `threads/`（中に plans 一式とスレッド置き場を持つ）。plans を単独で導入済みのリポジトリへの移行手順も README に書くか決める。
- **場面**: スレッド作成（プラン分割前） / 実行中の追記（事実の発覚・仕様変更・手戻り・プランの追加・順序変更） / スレッドのクローズ。プランの作成・実行は plans の guides をそのまま使う。
- **成果物**:
  - スレッドファイル（`type: Thread`）。1スレッド＝1ファイルか1フォルダかを決める（時系列記録が長くなる場合の分割方法も）。
  - 本文の節（候補）: 目的・スコープ / プラン一覧と順序 / 未解決事項 / 経緯（時系列、追記のみ）。
  - 経緯エントリの書式（候補）: `### YYYY-MM-DD [種別] 見出し` ＋ 1〜3行 ＋ 反映先プランへのリンク。種別は 計画・発見・仕様変更・手戻り・順序変更・完了 など少数の固定値。
  - frontmatter（候補）: スレッド側 `status`（例: `open` / `paused` / `closed` / `abandoned`）と `plans:`（所属プランの overview への相対パス、各項目にコメント）。プラン側 overview（単一ファイル完結ならそのファイル）に `thread:`（スレッドへの相対パス）。
- **不変条件（候補）**: スレッドの `plans` とプランの `thread` は対で更新する／経緯は追記のみで過去エントリを書き換えない（経緯の改ざんを防ぎ、手戻りの原因を後から追えるようにする）／発覚した事実は経緯に書いたうえで影響プラン本文へも反映する（plans の不変条件を維持）／スレッドに実装手順を書かない（実装はプランの役割）。

## 決定事項・注意点／落とし穴

- **完了プランの削除**: plans は完了プランを削除する。スレッドの `plans:` が削除済みパスを指すと lint エラーになる。候補: (a) スレッドが `open` の間は所属プランの削除を保留する、(b) 削除時に経緯へ完了要約を追記し、`plans:` から外して本文の「完了済みプラン」に名前だけ残す。plans のガイドは変更しない方針なので、threads 側のガイドで「スレッド所属プランの後片付け」を上書きとして定義する。
- **順序の正本**: plans では `order` は正本ではなく、着手条件の正本は `depends_on`。スレッドのプラン一覧の並び順を正本にすると plans と矛盾する。スレッドの一覧は「予定順の表示」、着手条件の正本は引き続き `depends_on` とし、lint で一覧順と `depends_on` が矛盾しないことを検査する案を推す。
- **snapshot との関係**: 着手済みプランの仕様変更は plans の規約どおりプラン本文を書き換える（snapshot は触らない）。完了済み（削除済み）プランへの手戻りは新しいプランを起こしてスレッドに追加する。
- **フォルダ名**: overview の未決事項。`threads` テンプレートの中にスレッド置き場を `threads/` で置くと `threads/threads/` になる。
- **Step 1 依存**: コピー先構成とフォルダ名は取り込み方式（A/B/C）で変わる。

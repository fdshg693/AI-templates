# template-review

テンプレートフォルダを下記の基準で評価し、根拠（`ファイル:行`）と修正案付きで報告する。**評価のみ行い、編集はしない**。修正はユーザーが指示した項目だけ行う。新しいテンプレートを作るときは [template-create](../template-create/SKILL.md) を使う。

## 手順

1. 対象を決める。指定が無ければ `core/` 直下の各フォルダを1つずつ評価する。
2. 機械的チェックを実行する（リポジトリルートで）:

   ```bash
   uv run .claude/skills/template-review/scripts/inspect_template.py core/<name>
   ```

   リンク切れ・フォルダ外へのリンク・入口からのホップ数と到達不能ファイル・常時ロードされる行数（AGENTS.md + CLAUDE.md）・reference 間の近似重複・ファイル間の重複行・同梱スクリプトの状態・プレースホルダを列挙する。事実の列挙なので、判定は自分で行う。
3. 典型タスクを1つ想定し（例: plans なら「新しいプランを書く」）、`AGENTS.md`（無ければ `CLAUDE.md`）から**リンクを辿って必要なファイルだけ**を読む。先に全ファイルを通読しない（通読すると Progressive Disclosure の欠陥が見えなくなる）。読んだファイル数・行数を記録する。
4. 残りのファイルを読み、各基準を A / B / C で判定する。
5. 下記の形式で報告する。

## 評価基準

判定: **A** = 問題なし / **B** = 改善余地あり（作業はできる） / **C** = 作業に支障がある、または誤った成果物を誘発する

### 1. reference が必要最小限か

- reference だけ見て、新しいファイルを同じ書式・粒度で書けるか（書き方が一意に定まるか）
- 各 reference が他と異なる「書き方の判断」を示しているか。題材や状態が違うだけで書き方が同じものは統合候補（スクリプトの近似重複を参照）
- reference にルール本文が混入していないか。ルールはガイド/AGENTS.md、reference は例に徹する
- 骨格と記入例を両方持つ場合、両方必要か

### 2. AGENTS.md / CLAUDE.md 対応と README との責務分担

- CLAUDE.md は `@./AGENTS.md` のエイリアスで、正本は AGENTS.md の1つか
- AGENTS.md だけで、フォルダの目的・場面ごとに読むファイル・守るべき不変条件が分かるか
- AGENTS.md に人間向けの背景・経緯が多すぎないか（常時ロードされる。目安150行以内）
- README は「何のテンプレートか・誰向けか・導入方法」に集中し、エージェント向けルールを重複して持っていないか。食い違いが無いか
- テンプレート置き場での編集時とコピー先での利用時、どちら向けの指示かが明確か（パス表記の差など）

### 3. Progressive Disclosure

- AGENTS.md に「場面 → 読むファイル」の対応があるか
- 参照がリンクで張られているか（「`references/` 配下を参照」のような曖昧な指示だけになっていないか）
- 典型タスクで読む量がタスクに見合っているか。通読前提になっていないか
- 到達不能なファイル、深すぎる（3ホップ超で必須情報に届く）構造が無いか
- 1ファイルに複数場面が詰め込まれていないか／逆に細切れすぎないか

### 4. 自動化

- 手順中の機械的な作業（整合確認、コピー・リネーム、採番、スナップショット、リンク検査など）が手作業のまま残っていないか。残っていれば自動化候補として具体的に挙げる
- 同梱スクリプトが、実行コマンドと実行タイミング付きで AGENTS.md かガイドに書かれているか
- `--help`・docstring があり、標準ライブラリのみ（または PEP 723 で `uv run` 一発）で動くか
- 失敗時に非0終了し、`ファイル:行` でエラー箇所を示すか（エージェントが修正ループを回せるか）
- 必要なら reference 一式に対して実際に実行して確かめる

### 5. 正本の一意性（追加）

- 各ルール（書式・状態値・手順）の正本が明示され、他の場所は要約＋リンクに留まっているか
- 状態値や用語の一覧がガイド・スクリプト・README 間で食い違っていないか

### 6. 移植性（追加）

- リンク切れ、フォルダ外へのリンクが無いか。他テンプレートへの依存があるなら明記されているか
- 元リポジトリ固有のスキル・ツール・ドメイン用語が残っていないか。残すなら「固有なので無視してよい」と明記されているか
- 特定の AI ツール・OS・言語を暗黙に前提にしていないか

### 7. 導入手順の明確さ（追加）

- 何をコピーし、何をリネーム・削除し、どのプレースホルダを置き換えるかが分かるか
- プレースホルダの記法が統一されているか（`{x}` と `<x>` の混在など）
- 導入直後にやること（スクリプト実行、初回作業）が書かれているか

### 8. 指示の検証可能性（追加）

- ルールが「適切に」「意識する」ではなく、確認できる行動・成果物（ファイル、frontmatter 値、チェックボックス）で書かれているか
- 完了条件・ゲートが明示されているか
- 禁止事項に1行の理由があるか（無いとエージェントが例外判断できない）

### 9. フォルダ構造と命名（追加）

- フォルダ構成が役割（ガイド・reference・スクリプト・入口ファイル）ごとに分かれ、どこに何を置くか一目で分かるか
- フォルダ名・ファイル名から中身が推測できるか。中身と名前が食い違っていないか
- 命名規則（ケース、単数/複数、言語、採番の桁数など）がフォルダ内で統一されているか
- 不要な階層や、1ファイルしか入っていないフォルダが無いか

### 10. reference 準拠チェックスクリプト（追加・nice-to-have）

- コピー先で作られた成果物が、そのテンプレートの reference（書式・frontmatter・必須セクション・フォルダ構造など）に沿っているかを検査するスクリプトが提供されているか
- そのスクリプトを reference 一式に対して実行すると通り、意図的に崩したファイルでは失敗するか（＝エージェントの出力が reference に沿ったかを実際にテストできるか）
- nice-to-have のため、無いことだけを理由に C にはしない（無ければ B として、検査すべき項目を具体的に挙げる）

## 報告形式

```markdown
# <テンプレート名> 評価

| 基準 | 判定 | 要点 |
| ---- | ---- | ---- |
| 1. reference の最小性 | B | ... |
| ... | | |

典型タスク「...」: 入口から N ファイル / M 行を読んで着手できた（できなかった理由: ...）

## 改善提案（優先度順）

1. **[C] 指摘の要約**（基準 #）
   - 根拠: `path:line` ...
   - 修正案: ...
```

- 優先度は C → B の順、同じ判定内では影響範囲の広いものから
- 「分かりにくい」だけの指摘はしない。必ず根拠の位置と具体的な修正案を添える
- テンプレートが意図的に固有情報を含むと宣言している場合（例: plans の README）は、その宣言の妥当性を評価する
